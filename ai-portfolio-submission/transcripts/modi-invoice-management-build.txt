--- ASSISTANT ---
It doesn’t connect to Wi‑Fi itself — that stays with the OS (macOS Wi‑Fi / ethernet). The app only **detects** whether you’re already online.

In [`src/lib/network.ts`](src/lib/network.ts) it does two things:

1. **`navigator.onLine`** — browser/Electron flag for “network interface looks up,” plus `online` / `offline` events when that changes.
2. **A quick internet probe** — `fetch('https://www.gstatic.com/generate_204', { mode: 'no-cors' })` with a short timeout, so it’s not only “Wi‑Fi connected” but “can reach the internet” (needed for Supabase).

That status feeds the **Online / Offline** pill in the top bar and the Database page. If offline, **Connect database** stays disabled, because a cloud Postgres URL won’t work without internet.

So: Wi‑Fi join = your Mac; our code = “are we online enough to talk to the DB?”

--- ASSISTANT ---
Two separate problems: **who the bill is for**, and **how to read different PDFs**.

### 1. Business side (shop → vendors)
Today your app is built for **customers (parties)** who owe *you* (sales + receipts).

Vendor bills are the opposite:
- **Vendor** = supplier you buy from  
- Bill = money **you owe them** (purchase / expense)  
- Payment = money **you pay them**

So you’d mirror the party model: **Vendors** with their own invoices + ledger (purchases Debit your liability / payments Credit). Don’t mix them into the same customer parties list.

---

### 2. Reading different vendor bills correctly
Your current extractor in [`src/lib/pdfExtract.ts`](src/lib/pdfExtract.ts) is **hard-coded for MODI tax invoices** (`Party Name`, `Bill No`, that line-item pattern). Other vendors will use different labels, column orders, and layouts — one regex set will keep failing.

**Reliable approach for a shop with many vendors:**

**A. Per-vendor PDF templates (best for correctness)**  
For each frequent vendor, save a small parser config, e.g.:
- How to spot that vendor (GSTIN, header name, logo text)
- Where “Invoice No”, “Date”, “Grand Total” appear (labels / regex)
- How line items are structured  

Flow:
1. Upload PDF → extract raw text  
2. Detect vendor (GSTIN / name match against your vendor list)  
3. Run **that vendor’s** parser  
4. Always show a **confirm/edit screen** before save (you already do this — keep it; it’s the safety net)

**B. Confirm step is mandatory**  
Even with good parsers, treat extraction as “draft”. Staff fix wrong amounts/dates. That’s how you stay accurate when a vendor changes their format.

**C. Start with your top 5–10 vendors**  
Don’t try to auto-read every PDF in India. Add templates as you see real bills. Unknown vendor → manual entry (or generic “best effort” + heavy confirm).

**D. Optional later: AI / OCR**  
Useful for scanned image PDFs or weird layouts. Still keep confirm + vendor template when possible; AI alone isn’t enough for accounting.

---

### Practical rule
| Situation | What to do |
|-----------|------------|
| Known vendor, known layout | Template parser → confirm → save |
| New vendor | Create vendor + template from 1–2 sample bills |
| Layout changes | Update that vendor’s template |
| Unreadable / scan | Manual entry |

So: **correctness comes from vendor-specific templates + always confirming**, not from one universal “read any bill” function.
